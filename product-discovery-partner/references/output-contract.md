# 输出合同

这个文件定义什么情况下输出什么产物。默认不是“写一份完整 PRD”，而是“回答用户当前真正需要的问题”。

## 1. 四层产物

| 层级 | 产物 | 主要用途 | 何时使用 | 长度 |
|---|---|---|---|---|
| L0 | 决策备忘（一页纸 brief） | 判断该不该做、继续还是停止 | 快速档、决策门为 PAUSE/STOP、用户问“值不值得做” | 1–2 页 |
| L1 | 精简 PRD | 对齐小团队、准备做 MVP | 标准档、决策门为 CONTINUE/NARROW | 5–10 页 |
| L2 | 完整 PRD | 融资、招聘、多团队协作、复杂产品 | 决策门为 CONTINUE，且用户明确需要 | 10–25 页，按需选章节 |
| L3 | Build Spec | 交给 coding agent 或工程团队执行 | 准备开发、需要验收标准和数据模型 | 按模块组织 |

不要因为用户说“帮我写 PRD”就默认 L2。先判断用户要的是决策、对齐还是执行。

## 2. 输出前的决策门

写任何 L1/L2/L3 之前，必须先有决策门结果。

- CONTINUE：可以进入 L1/L2/L3。
- NARROW：先收窄范围，再进入 L1。
- PIVOT：先给出替代路径，不要直接写当前方向的 PRD。
- PAUSE：输出 L0 + 验证包，不写完整 PRD。
- STOP：输出 L0，说明停止理由，不写 PRD。

如果用户坚持要 PRD，可以写，但必须：

- 在开头标明“这是基于未验证假设的草稿”。
- 列出最危险的 3 个假设。
- 说明哪些部分不能用于开发决策。
- 附上 kill criteria。

## 3. 状态标签

每个事实性判断都要带标签：

- `[已验证 F-01]`：有证据支持，注明来源。
- `[假设 A-01]`：合理但未验证，附验证方式。
- `[猜测 G-01]`：助手推断，明确说明可能错。
- `[待确认 Q-01]`：需要用户回答。
- `[外部来源 R-01]`：公开来源，附 URL 和日期。

标签不是装饰。没有标签的事实性判断视为未验证。

## 4. 假设清单

假设清单是核心产物，不是附录。放在决策备忘或 PRD 的前部。

| ID | 假设 | 风险 | 现有证据 | 验证方式 | 阈值 | 状态 |
|---|---|---|---|---|---|---|
| A-01 | 用户愿意为节省 4 小时/周付费 | 高 | E0 口头兴趣 | 5 个用户预售 | ≥2 人预付 | 未验证 |
| A-02 | AI 能从聊天记录中稳定提取需求 | 高 | 无 | 50 条样本评测 | 关键字段准确率 ≥85% | 未验证 |

排序规则：风险 × 不确定性 × 对决策的影响。最危险的假设放最前面。

## 5. L0 决策备忘

必须包含：

- 判断：CONTINUE / NARROW / PIVOT / PAUSE / STOP。
- 置信度：高 / 中 / 低。
- 一句话理由。
- 目标用户和问题。
- 最强证据（带 ID）。
- 最大风险 / 最强反方论据。
- 最窄切口（如果继续）。
- 下一步最便宜的验证。
- Kill criteria。
- 什么证据会改变判断。

模板：`outputs/decision-memo.md`。

## 6. L1 精简 PRD

建议 8–10 节：

1. 一句话总结。
2. 目标用户与问题。
3. 证据与现状替代。
4. 最窄切口与价值主张。
5. MVP 范围与非目标。
6. 核心用户路径。
7. 技术与 AI 方案（简版）。
8. 指标与成功标准。
9. 风险、假设与验证计划。
10. 下一步。

不要为了凑章节写不相关的内容。模板：`outputs/lean-prd.md`。

## 7. L2 完整 PRD

只在以下情况使用：

- 决策门为 CONTINUE。
- 需要融资、招聘、多团队协作或正式评审。
- 用户明确要求完整 PRD。
- 关键假设已经有至少 E1/E2 证据，或已明确标为待验证。

### 章节选择器

不要机械写 25 节。按产品类型选择：

| 产品类型 | 必选章节 | 可省略 |
|---|---|---|
| AI 产品 | 用户/问题、证据、切口、AI 角色、输入输出、质量与失败兜底、数据、评测、成本/延迟、UX、技术栈、指标、风险 | 复杂企业权限（如果 To C） |
| Marketplace | 供需两侧、信任、支付/托管、争议处理、匹配、冷启动、运营后台、风控 | 复杂 AI 能力（如果不相关） |
| 内部工具 | 工作流、角色权限、数据边界、集成、操作日志、异常处理、采纳指标 | 消费者增长、品牌 |
| B2B SaaS | 使用者/购买者/决策者、安全、权限、集成、后台、定价、采购流程 | 消费者社交增长 |
| 移动 App | 平台、入口、通知、离线、权限、商店审核、留存循环 | 复杂企业后台 |
| 受监管产品 | 牌照/备案、数据合规、内容审核、审计、人工复核、风险分级 | 过早的增长细节 |

模板：`outputs/full-prd.md`。模板本身也是可裁剪的，不是检查清单。

## 8. L3 Build Spec

给 coding agent 或工程团队的 spec 必须包含：

- 产品目标和成功标准。
- 用户故事。
- Given/When/Then 验收标准。
- 数据模型：实体、字段、关系、约束。
- API / 事件：输入、输出、错误码、幂等。
- 权限和角色。
- 核心状态机。
- 空状态、加载、错误、重试、回滚。
- AI 输入、输出、评测集、失败兜底、人工确认。
- 非功能需求：性能、安全、隐私、可观测性。
- 测试计划。
- 分阶段交付和回滚策略。

模板：`outputs/build-spec.md`。

## 9. 证据附录

L2/L3 可以附证据附录，但不要把核心判断埋在附录里。

附录包括：

- 证据账本。
- 研究来源。
- 访谈摘要（脱敏）。
- 验证结果。
- 仍未解决的问题。

## 10. 质量检查

输出前检查：

- 开头是否明确回答了用户的问题？
- 是否有决策、置信度和理由？
- 是否有假设清单，并按风险排序？
- 是否每个关键事实都有标签？
- 是否写了非目标？
- 是否写了 kill criteria？
- 是否区分了用户已确认、助手推断、助手建议和待确认？
- 是否避免了“看起来完整但没有证据”的章节？
- 工程师或设计师能否据此开始工作？
- 如果决策是 PAUSE/STOP，是否避免了写完整 PRD？

## 11. 常见错误

- 用户说“写 PRD”，就直接写 25 节。
- 把假设写成事实。
- 为了完整性加入不相关章节。
- 只写功能，不写失败状态和权限。
- 指标是虚荣指标，和用户价值无关。
- 没有非目标，导致范围膨胀。
- 没有 kill criteria，项目无法停止。
- 把决策备忘写成 PRD 的摘要，而不是独立判断。
