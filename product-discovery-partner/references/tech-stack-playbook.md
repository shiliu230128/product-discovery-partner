# 技术栈 Playbook

技术建议要服务产品阶段、团队能力和风险，而不是追求“先进”。

## 1. 原则

- **成熟默认**：除非新技术带来明确产品优势，否则优先选择团队能掌控、社区成熟、容易招聘和维护的技术。
- **可逆优先**：早期尽量选择可替换方案。不可逆或迁移成本高的决策要明确写入 PRD。
- **完整而不过度**：如果补齐错误处理、日志、权限、测试和后台只多一点成本，就不要推到以后。
- **先验证价值，再扩架构**：不要为还没验证的需求提前搭复杂平台。
- **用户结果优先**：技术栈服务用户结果，不服务技术炫技。
- **可观测是产品能力**：关键路径必须能看到成功、失败、延迟、成本和用户行为。
- **合规是范围的一部分**：受监管产品先确认牌照、备案、数据和内容要求，再选架构。

## 2. 先问清的决策变量

- 目标平台：Web、移动端、小程序、桌面端、插件、机器人、API-first。
- 团队最熟悉的技术。
- 上线时间、预算、预期用户规模。
- 数据来源、敏感度、保存期限。
- 是否需要权限、审计、合规。
- 是否需要支付、订阅、发票。
- 是否需要实时协作、通知、离线。
- 是否需要第三方集成。
- 是否需要后台运营。
- 是否需要 AI，以及 AI 的角色。
- 哪些选择可逆，哪些不可逆。
- 哪些能力可以先人工或半自动验证。

## 3. 可逆性分级

### 容易回滚

- UI 框架和组件库。
- 分析工具。
- 邮件/通知服务。
- 静态内容站。
- 早期数据库 schema（有迁移工具时）。

### 中等成本

- 数据库类型。
- 鉴权方案。
- 支付服务商。
- 云厂商。
- 前端/后端拆分方式。

### 难以回滚

- 数据模型和租户隔离。
- 权限模型。
- 核心工作流状态机。
- 自建模型/私有化部署。
- 深度平台集成。
- 合规架构。

难以回滚的决策，要在 PRD 中写明假设、替代方案和切换成本。

## 4. Web SaaS MVP

默认建议：

- 前端：Next.js + TypeScript + React + Tailwind。
- 后端：Next.js API routes / server actions，复杂后端再拆服务。
- 数据库：Postgres。
- ORM：Prisma 或 Drizzle。
- 鉴权：Clerk 或 Auth.js。
- 支付：Stripe（海外）或微信支付/支付宝（中国）。
- 分析：PostHog 或同类。
- 部署：Vercel 或云平台。
- 监控：Sentry + 平台日志。

适合：快速验证、B2B SaaS、AI Web 产品、创始团队。

质量闸门：

- 关键用户路径有埋点。
- 错误状态对用户可见。
- 管理员能处理异常数据。
- 重要数据有导出能力。
- 核心功能有自动化测试或明确测试计划。
- 权限和租户隔离从第一天就有基本设计。

## 5. AI Web 产品

默认建议：

- Web 层：Next.js + TypeScript。
- 模型层：Vercel AI SDK 或同类抽象层。
- 数据库：Postgres。
- 向量检索：pgvector 起步，规模变大再考虑专用向量库。
- 文件存储：S3/R2/Blob。
- 任务队列：需要长任务时引入队列。
- 评测：建立小型 eval set。
- 成本：记录每次调用的 token、耗时、模型、结果质量。

关键取舍：先做质量闭环，再追求复杂 Agent。

早期先证明：

- 用户愿意提供真实输入。
- 输出能节省真实时间。
- 用户愿意编辑、采纳或分享结果。
- 错误可被发现和修正。

## 6. AI Agent 产品

必须设计：

- 工具调用权限。
- 任务状态机。
- 人工确认节点。
- 失败重试。
- 审计日志。
- 回滚或撤销。
- 成本上限。
- 可观测性。
- eval harness。

不要让 Agent 在没有边界的情况下直接执行高风险动作。

默认安全策略：

- 建议优先于执行。
- 草稿优先于发布。
- 人工确认优先于全自动。
- 可撤销优先于不可逆。
- 记录每一步优先于黑盒执行。

高风险动作包括：发消息、发邮件、发布内容、修改生产数据、扣费/退款、删除数据、调用外部系统产生不可逆影响。

## 7. RAG 产品

必须设计：

- 数据源。
- 文档切分。
- 元数据。
- 权限过滤。
- 召回策略。
- 重排。
- 引用来源。
- 答案置信度。
- 评测集。
- 用户反馈闭环。

MVP 可用 Postgres + pgvector 起步。RAG 的核心体验不是“能回答”，而是“回答可信”。权限过滤和引用来源要写进产品需求。

## 8. 内部工具

默认建议：

- 极早期：Retool / Appsmith / 飞书多维表格。
- 定制化：Next.js + Postgres + RBAC。
- 必备：操作日志、权限、导入导出、异常处理。

原则：不要把内部工具做成漂亮但难维护的 SaaS。

内部工具的常见失败不是界面不够漂亮，而是权限、异常处理、操作日志和数据修正能力缺失。

## 9. 移动产品

默认建议：

- MVP：React Native / Expo。
- 强原生能力：Swift / Kotlin。
- 后端：Postgres + API。
- 推送：平台推送服务。
- 分析：移动端事件埋点。

判断是否必须原生：

- 是否重度使用系统能力。
- 是否需要极致性能。
- 是否要求复杂离线体验。
- 是否需要深度后台运行、蓝牙、相机/传感器等。

中国区还要考虑：

- iOS/Android 商店审核。
- 隐私政策和权限说明。
- 推送通道（厂商推送）。
- 实名认证、内容审核（如涉及）。
- 微信/支付宝 SDK 和合规。

## 10. 企业 B2B

优先考虑：

- SSO/SAML。
- RBAC。
- 审计日志。
- 数据隔离。
- Webhook。
- 队列。
- 监控。
- 备份。
- 合规路径。

不要用只适合消费级 MVP 的方案承诺企业级能力。

分层建议：

- MVP：基础团队权限。
- V1：审计日志、角色权限。
- 企业版：SSO/SAML、数据隔离、合规流程、私有化。

## 11. Marketplace

技术重点：

- 身份认证。
- 支付/托管。
- 评价系统。
- 争议处理。
- 供需匹配。
- 运营后台。
- 风控。

冷启动比技术更关键，PRD 中必须写运营策略和首批供需从哪里来。

## 12. 工作流自动化

必须设计：

- 触发器和事件。
- 队列和任务编排。
- Webhook。
- 重试和幂等。
- 操作日志。
- 人工介入。
- 失败告警。
- 权限和审计。

自动化越强，越需要“暂停、回滚、人工接管”。

## 13. 中国技术环境

涉及中国市场时，额外考虑：

### 平台入口

- 微信小程序 / 公众号 / 企业微信。
- 飞书 / 钉钉。
- 抖音 / 小红书。
- App / Web。
- 线下/渠道。

### 合规

- ICP 备案、公安备案。
- 生成式 AI 服务备案/算法备案（按适用情况）。
- PIPL、数据安全法、网络安全法。
- 数据出境。
- 个人信息、未成年人、内容审核。
- 实名认证。
- 隐私政策、用户协议。

### 支付

- 微信支付、支付宝。
- 发票。
- 订阅/按量/服务费。
- 苹果 IAP（iOS 虚拟服务）。

### AI

- 国内模型/云服务。
- 内容安全。
- 私有化/信创。
- 模型备案。
- 成本、延迟和数据驻留。

### 增长

- 私域、企微、社群。
- 渠道/代理。
- 行业活动。
- 内容种草。
- 应用商店/小程序审核。

法规和平台规则会变化，必须查官方最新信息；本文件不构成法律意见。

## 14. Build Spec 交接

技术栈确定后，交给 build spec 的内容：

- 平台和部署拓扑。
- 数据模型和权限模型。
- API/事件。
- 状态机。
- 第三方集成。
- 非功能需求。
- 监控和回滚。
- 测试计划。

不要让 coding agent 从“推荐技术栈”直接开始写代码；先给它可验收的 spec。

## 15. 常见错误

- 为了“先进”引入团队无法维护的架构。
- 早期自建模型/向量库/工作流引擎。
- 没有权限和租户隔离，后期重写。
- 没有错误处理、日志和后台，导致运营靠手工改数据库。
- 把合规留到上线前。
- 用消费级方案承诺企业级安全。
- 技术选型没有和产品阶段、团队能力、上线时间绑定。
