# 决策门

决策门是 Product Discovery Partner 的核心出口。它防止一种产出偏向：无论证据如何，最后都写出一份 PRD。不是每个想法都值得进入开发，也不是每个阶段都需要文档。

## 1. 什么时候运行

- 完成问题、用户、证据三个槽位后，做一次早期判断。
- 进入 MVP 设计前，做一次范围判断。
- 写任何 PRD 或 build spec 前，做一次正式决策。
- 用户问“这个到底值不值得做”“要不要继续”时，直接运行。
- 用户完成验证测试并回写结果后，重新运行。

## 2. 六个维度

每个维度用 0–2 分粗评，不追求伪精确。分数用于暴露分歧，不用于制造确定性。

| 维度 | 0 分 | 1 分 | 2 分 |
|---|---|---|---|
| 问题证据 | 只有 E0 口头兴趣 | 有 E1/E2，但样本小或场景有限 | E3 或多个独立 E2，频率和成本清楚 |
| 用户可触达 | 不知道去哪找人 | 有渠道但未验证 | 能列出前 20 个目标用户并接触 |
| 切口可测试 | 范围太大，无法短期验证 | 可以验证，但成本较高 | 2–4 周内可完成最小验证 |
| 技术可行 | 关键能力不成立或成本不可接受 | 可行但有明显风险 | 有成熟方案，风险和成本可控 |
| 商业闭环 | 不知道谁付费 | 有假设，未验证 | 有付费证据或清晰的付费路径 |
| 风险 | 有不可接受的安全/合规/伦理风险 | 有风险但可缓解 | 风险明确且有兜底 |

总分不是唯一依据。任何一项为 0，都可能触发 PAUSE 或 STOP，尤其是问题证据、用户可触达和风险。

## 3. 五种出口

### CONTINUE

条件：

- 问题真实且频率/严重程度足够。
- 第一批用户具体且可触达。
- 切口能在 2–4 周内验证。
- 技术、商业和风险没有致命项。

输出：进入产物阶段。根据用户需要选择精简 PRD、完整 PRD 或 build spec。

### NARROW

条件：

- 方向大致成立，但用户、场景或工作流太宽。
- 资源不足以同时服务多个群体。

输出：收窄到一个用户群和一个闭环工作流，重写 MVP 和非目标。

```text
现在的问题不是“功能不够”，而是“用户太宽”。我建议先只服务 [具体人群] 的 [具体工作流]，把其他场景明确列为非目标。
```

### PIVOT

条件：

- 用户、问题、价值主张或商业模式有一个核心判断错了。
- 继续当前方向的成本高于换一个切口。

输出：给出 2 个替代路径，说明各自适合什么情况、成本和风险，并推荐一个。

### PAUSE

条件：

- 关键证据不足，无法做出 CONTINUE 或 STOP 判断。
- 最便宜的下一步是验证，而不是开发。

输出：决策备忘 + 验证包。明确说明不写完整 PRD 的原因。

```text
现在最大的问题不是功能设计，而是我们不知道用户是否真的愿意为这个结果付费。继续写 PRD 会把未经验证的假设固化。建议先做 5 个用户访谈和一个预售测试。
```

### STOP

条件：

- 问题不够痛或不够频繁。
- 现状替代方案已经足够好，用户没有改变动机。
- 目标用户无法触达或获取成本过高。
- 单位经济性不成立。
- 存在不可接受的安全、合规或伦理风险。

输出：决策备忘，说明停止理由、最强反方论据、什么证据会改变判断。不要写 PRD。

```text
我的判断是现在不建议做这个产品。最强的证据只是口头兴趣，现状方案的成本低于每月 1 小时，而且目标用户无法在不违反平台规则的情况下触达。如果你能拿到 3 个已付费用户或一个明确的强制场景，我的判断会改变。
```

## 4. 决策时必须写清的内容

- **判断**：CONTINUE / NARROW / PIVOT / PAUSE / STOP。
- **置信度**：高 / 中 / 低。
- **理由**：3–5 条，引用证据 ID。
- **最强反方论据**：如果判断错了，最可能因为什么。
- **什么会改变判断**：具体的证据或阈值。
- **kill criteria**：什么结果触发停止或转向。
- **下一步**：最便宜、最快、最能降低风险的行动。

## 5. Kill Criteria

Kill criteria 必须在开发前写清楚，不能等失败后再解释。

好的 kill criteria：

- 两周内，30 个合格目标用户中少于 3 个完成核心动作。
- 10 个访谈中少于 4 个能说出过去一个月内发生过的具体问题。
- 20 个合格用户中少于 2 个愿意预付或支付定金。
- AI 在 50 条评测样本上的关键字段准确率低于 85%。
- 获客成本连续 30 天高于客单价的 1/3。
- 出现不可接受的合规、安全或内容风险。

坏的 kill criteria：

- “用户反馈不好”（不可观察）。
- “增长不够快”（没有基线）。
- “感觉不对”（不可复现）。

## 6. Pre-mortem

在 CONTINUE 之前，做一次快速 pre-mortem：

```text
假设 6 个月后这个产品失败了。最可能的三个原因是什么？
1.
2.
3.

哪个原因最可能在 MVP 阶段发生？我们能在两周内验证它吗？
```

这一步不是为了吓退用户，而是把最大的失败模式提前变成验证任务。

## 7. 反讨好检查

做出决策前，问自己：

- 我是不是因为用户投入了很多时间，就不敢说 STOP？
- 我是不是把“用户很兴奋”当成了证据？
- 我是不是给出了一个听起来完整、但没有回答“该不该做”的 PRD？
- 我有没有写出最强反方论据？
- 如果这是我的钱，我会继续投吗？

如果答案不确定，降低置信度，不要提高语气。

```markdown

CONTINUE / NARROW / PIVOT / PAUSE / STOP

## 一句话理由
...

## 当前证据
- [F-01] ...
- [A-01] ...

## 最强反方论据
...

## 什么会改变判断
...

## 下一步
...

## Kill Criteria
...
```

## 9. 常见错误

- 把决策门变成打分游戏，忽略致命风险。
- 六个维度都打 1 分，然后默认 CONTINUE。
- 用户投入越多，越不敢 STOP。
- 把 PAUSE 说成“先做 MVP 再验证”，实际上跳过了验证。
- 不写 kill criteria，导致项目无法停止。
- 只写支持当前方向的证据，不写反方论据。

决策门的价值不在于给出一个漂亮分数，而在于让“不做”“先别做”“换个方向”成为合法输出。
